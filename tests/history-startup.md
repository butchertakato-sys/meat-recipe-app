# 起動時同期と製造履歴表示の検証

対象の改修前main: c985911f14b93df75a5d4566899e88241bb9f15e。

原因: startApplicationの同期完了後でも、refreshManufacturingHistoryが毎回runCrossDeviceIntegrationを呼び、旧端末データとの照合GETとIndexedDBキャッシュ取得GETを待っていた。Promiseは実行中の重複を防ぐが、完了後の再閲覧は新規同期となっていた。また、同期の前後で端末履歴を2回取得していた。

変更: 起動時のPromiseをアプリの生存期間中保持し、通常の履歴閲覧はその完了後に端末データを1回取得する。手動更新だけが既存の統合処理を要求し、既存Promiseを共有する。既存の通信タイムアウト、統合・削除・未同期保護、ID/LOT処理は変更しない。失敗時も端末履歴を表示し、失敗状態と以前の成功日時を区別する。定期タイマーや復帰時の同期は追加しない。

## 計測

改修前に正式workspaceのコードを隔離Chromiumで実行し、合成Supabaseの製造履歴GETへ各200msの遅延を与えた。起動同期完了後の履歴閲覧は426ms、製造履歴GET 2回、クラウド要求全体4回だった。

新規テストは同条件で同期完了後の閲覧時間を出力し、クラウド要求0回と不要な400ms待機の不存在を検証する。改修後の計測例は6ms。固定の処理速度や本番ネットワークの改善率を保証する測定ではない。データ量・端末性能により端末内の処理時間は変わる。

## 必須18項目の対応

| 番号 | 検証場所 |
|---|---|
| 1～6 | history-startup-integration.cjs: 認証を模したinitApp起動、実メニュー操作、起動中更新要求、実ボタン連打、描画回数、クラウド要求 |
| 7～10 | 同テスト: 手動更新中のホーム遷移、起動中詳細表示、通信失敗、既存15秒deadlineのテスト内短縮、オフライン起動 |
| 11～13 | record-observation-integration.cjsとsync-integration.cjs: tombstone優先、同LOT別ID、古いGETからの復活防止、未同期/syncing/新しい端末データの保護 |
| 14 | 既存両統合テスト: 新規保存、編集、削除、再送信時のID/LOT/snapshot維持 |
| 15～16 | history-startup-integration.cjs: ブラウザ時計の2時間進行、hidden→visible、pageshow、startApplicationの再呼出し、同期回数と要求の不変 |
| 17 | 同テスト: 成功日時の存在、通信失敗/deadline後の旧日時維持、成功/失敗metaの区別 |
| 18 | 同テスト: 各GET200ms遅延条件での計測と同期完了後のクラウド要求0回 |

実際のバックグラウンド統合が終了しても、表示済み一覧のHTMLと描画回数が変わらないことも検証する。既存の保存時重量表示、分析一覧の仕込み日・マスタ重量、削除済み除外、診断GET専用性のテストを維持する。

npm testで77単体テストと3本のブラウザ統合テストを実行する。ブラウザは全通信をrouteし、app.testの正式workspaceの静的ファイルとsupabase.testのメモリ内データのみを使用する。本番Supabaseはアクセスしない。テスト用時計・遅延・認証・故障注入はテストプロセス内だけであり、本番コードへタイマーを追加しない。

実機固有のSafari/iOSによる中断・再開、端末のストレージ容量・性能、実回線とログインセッションの影響は本テストの保証外。DB側の同時更新保護やGET/POSTの非原子性は今回の対象外で、完全な競合防止を保証しない。
